## Packages used:
- rich: for polished, colored prompts
- request: for handling requests
- python-dotenv: for reading environment variables
- click: a framework for building command-line tools. It handles parsing commands, arguments, and options with minimal code. (Removed because unused)
- psutil: reads real-time information about the computer's hardware and running processes.
- prompt_toolkit: for interactive input completion, autocompletion



## Provider:
OpenRouter (will use Local LLM later)

## Stages:

Stage 1 — Make it actually agentic (the big one)
Right now you type /run, R.A.V.E.N never decides to. This is the real "Agent" letter in R.A.V.E.N.

Tool-calling: let the LLM itself choose to call read_file/write_file/run_command based on your request, instead of you typing the slash command
Keep the confirmation step for /run — that's your negotiation safety net, don't lose it when this gets automated
This alone turns it from "chatbot with shortcuts" into an actual agent

Stage 2 — Memory

Persist conversation history to disk (SQLite is simplest) so context survives between runs
Later: let it recall past sessions ("what did we decide about the bookshelf design last week")

Stage 3 — More execution tools

list_dir, delete_file, git commands — natural extensions of what tools.py already does
Each is a small addition to the same file, no new architecture needed

Stage 4 — Specialization

Once general tool-use works, split behavior by task type (coding vs. research vs. planning) — this is your future agents/ folder, but only once there's a real reason one prompt style doesn't fit all tasks

Stage 5 — Other interfaces

A FastAPI wrapper around the same Assistant class, so a future desktop/web UI can reuse it without duplicating logic


## Functionalities

- reading files via the /read command
- writing files via the /write command
- commands auto completion
- "/" commands
- can read files from a prompt "read the file at file/path"
- can write files at /path/of/destination
- asks confirmations before running a command via /run
- user can cancel the request before the agent answers
- conversation history persists to ~/.raven/history.db between runs (only the last ~40 messages are sent to the model)
- agent tools: read/write/list/delete files, mkdir, run_command, git (write ops ask to confirm), open_app (launch installed desktop apps by name, no confirm)

* ### Step 3.8: Diagnosis — open_app picking the wrong app (Obsidian/VS Code instead of the actual text editor)
- root cause, confirmed by reproduction: _match_app()'s substring check was one-directional (`query in n`). Any extra word in the model's query ("text editor app" vs the installed name "text editor") made the query LONGER than the app name, so it could never be a substring — a silent "no match" on a request that should have resolved cleanly. A trailing period had the same effect.
- with the real query failing silently and no way to see what's actually installed, the model's retry was a blind guess from general knowledge (Obsidian, VS Code — both plausible "text editors", both happen to be installed) instead of an informed choice. Both open_app/open_file skip confirmation (by design, non-destructive), so the wrong guess launched immediately.
- fix 1: _match_app() now does whole-word containment both ways via _contains_words() (regex word tokens + set membership), not raw substring. First attempt (raw bidirectional substring) introduced a regression caught before shipping: a one-letter installed app named "R" substring-matched almost any query ("r" is inside "editor"); word-boundary matching fixes both problems at once. (tools.py)
- fix 2: on zero matches, _match_app() now offers difflib.get_close_matches() suggestions instead of a bare "no match" error, so a retry (if needed) is grounded in real installed names. (tools.py)
- fix 3: new list_apps() tool — lists every installed app's display name; SYSTEM_PROMPT now tells the model to try the user's generic phrase first, and if that fails, call list_apps and pick the closest real entry rather than guessing a specific brand from general knowledge. (tools.py, llm_provider.py, cli.py status phrase)
- verified live: "Open the text editor app for me." -> open_app(name="text editor") (the model's literal wording now round-trips correctly) -> launched the real Text Editor, not Obsidian/VS Code. "Open the note-taking app." (genuinely ambiguous) -> model called list_apps first, then picked a real installed name from the result instead of guessing a brand.

* ### Step 3.9: close_app — close a running application

* ### Step 3.18: Diagnosis — VS Code opens a new window instead of reusing one; closing "one" window closes all of them
- both stem from the same gap: open_app/open_file/close_app operate at the app/process level, no concept of individual windows.
- issue 1 (new window every open), fixed: VS Code's CLI opens a NEW window for a folder/file path by default — `-r`/`--reuse-window` is the documented flag to reuse the last active window instead. Deliberately did NOT live-test this by opening/closing extra windows in this environment: VS Code is already running here (likely this session's own host editor) and `code --status` failed against it ("can only be used if Code is already running", even though it clearly is — an unrelated environment quirk), so I couldn't safely verify window count without risking disruption to a possibly-real, possibly-in-use window. Implemented from documented CLI behavior instead, verified only at the Python/argv-construction level.
- REUSE_WINDOW_ARGS = {"code": ["-r"]} — small, keyed, extensible table (not a one-off special case) so another app needing similar treatment is a one-line addition. open_file() bypasses gtk-launch's %F template substitution entirely when extra args apply — that substitution's exact handling of a non-file flag like "-r" alongside a path isn't documented, so invoking the resolved binary directly (already confirmed on PATH via _binary_name + shutil.which) guarantees the argv gtk-launch's behavior otherwise couldn't guarantee. Falls back to the normal gtk-launch path for every other app. (tools.py)
- verified: mocked subprocess.Popen — VS Code call is exactly `['code', '-r', <path>]`; a different matched app (Code::Blocks) is untouched, still going through `['gtk-launch', 'codeblocks', <path>]`.
- issue 2 (closing one window closes all), NOT fixed — flagged for a decision: close_app works via `pkill -f <binary>`, which operates on PROCESSES, not windows. VS Code (and Electron apps generally) run ALL windows under one shared main process, so there is no process-level way to close "one window" — killing the process takes every window with it. A real per-window close needs a window manager tool (wmctrl/xdotool) to target a specific window by title; neither is installed, and this desktop is GNOME on Wayland, where GNOME Shell's Wayland compositor is well known for not reliably exposing legacy EWMH window-listing to XWayland tools like wmctrl (unlike e.g. KDE Plasma) — so even installing it carries a real chance of not working here. Didn't install anything or attempt a partial fix without the user's input, since adding a system package is a bigger, harder-to-reverse step than the code-only fixes so far. Asked the user how they want to proceed rather than guessing.

* ### Step 3.25: Crash — CLI died right after a browser-tool turn with "asyncio.run() cannot be called from a running event loop"
- reproduced the exact mechanism in isolation before touching any code: `sync_playwright().start()` left running (our design — the session persists across calls, never auto-closed) corrupts the main thread's asyncio state such that a later `asyncio.run(...)` call raises exactly this RuntimeError. (browser.py)
- secondary issue found while verifying the fix: at interpreter shutdown, atexit-registered close() could race against ThreadPoolExecutor's own internal exit handling and hit "cannot schedule new futures after shutdown" — confirmed harmless (checked directly: no chromium process left behind either way, since the OS reaps the whole process tree on exit regardless), but noisy. close() now catches that RuntimeError specifically and returns normally instead of a startling traceback on every exit.

## Clarifications

* MAX_TOOL_ITERATIONS (assistant.py): Without it, a single ask() call could loop forever.

The loop is: ask model → model calls a tool → feed result back → ask model again → maybe it calls another tool → repeat. There's nothing structurally stopping the model from just kept calling tools indefinitely — e.g. it misreads a file, keeps retrying to "understand" it, or gets into a confused back-and-forth where it never settles on a final text answer. Free/smaller models are more prone to this kind of not-quite-right behavior than larger ones.

Concretely, without the cap: one bad request could hang your terminal, burn through your OpenRouter rate limit (20 req/min free tier), and potentially run several confirmed shell commands in a row before you realize something's wrong.

MAX_TOOL_ITERATIONS = 5 just guarantees the function always returns — worst case you get "I hit the tool-call limit" instead of an infinite loop.
