## Stages (original plan — kept as written; current status and the revised plan are in "Stages — revised plan" below):

Stage 1 — Make it actually agentic (the big one)
Right now you type /run, R.A.V.E.N never decides to. This is the real "Agent" letter in R.A.V.E.N.

Tool-calling: let the LLM itself choose to call read_file/write_file/run_command based on your request, instead of you typing the slash command
Keep the confirmation step for /run — that's your negotiation safety net, don't lose it when this gets automated
This alone turns it from "chatbot with shortcuts" into an actual agent

Stage 2 — Memory

Persist conversation history to disk (SQLite is simplest) so context survives between runs
Later: let it recall past sessions ("what did we decide about the bookshelf design last week")

Stage 3 — More execution tools

list_dir, delete_file, git commands — natural extensions of what tools.py already does
Each is a small addition to the same file, no new architecture needed

Stage 4 — Specialization

Once general tool-use works, split behavior by task type (coding vs. research vs. planning) — this is your future agents/ folder, but only once there's a real reason one prompt style doesn't fit all tasks

Stage 5 — Other interfaces

A FastAPI wrapper around the same Assistant class, so a future desktop/web UI can reuse it without duplicating logic


## Stages — revised plan (2026-09-21)

Written after comparing R.A.V.E.N. against a pasted "Claude Code blueprint". Nothing was built in this step; it's a plan. Same rule as the original plan: **each stage starts only once the previous one is solid**, and nothing is added without a present need (YAGNI/KISS).

**Decision (user, 2026-09-21):** R.A.V.E.N. is to be both a general/desktop agent AND a coding agent, sequenced. Order: A, B, then C1 + C3, then D; E last and only with evidence of need. Rationale for not copying Claude Code feature-for-feature: the free models are weakest exactly where a coding loop is hardest (multi-step edit -> test -> fix), while desktop control, the isolated browser and Gmail are where R.A.V.E.N. is already distinctive.

### Baseline facts this plan rests on (measured 2026-09-21, not assumed)
- Fixed prompt overhead is ~4.2k tokens on EVERY request (system prompt ~1.3k + 26 tool specs ~2.9k; chars/4 estimate), before any history or user message.
- `read_file` and `run_command` return unbounded output, and context is trimmed by message COUNT (last 40), not tokens — one large file or build log can overflow the window.
- There is no test suite in the repo. Every check so far was an ad-hoc script in a temp folder that did not survive between sessions; results live in this log but nothing can re-run them.
- `grep`/`find` are not on the read-only command list, so every code search needs a confirmation; there is no dedicated search or edit tool (only whole-file `write_file`, which also overwrites without confirmation).
- The project is a git repo (1 commit, remote `origin`); `.env` is ignored and was never committed. That satisfies the preconditions for undo-by-git and, later, worktrees.
- The binding constraint on a coding loop is model reliability, not scaffolding: on the current free models we already saw wrong-app guesses, an invented "Firefox isn't installed" from stale context, a runaway reasoning spiral, and the tool-round cap hit. Expect multi-step edit/test/fix to be fragile until measured (A1).

### Deliberately NOT building (and why)
- **MCP** — reasoning unchanged from Step 3.27: value is reuse across many hosts/services; for one user it adds a protocol and subprocess layer on top of the wrapper code we'd write anyway. Revisit only if many third-party integrations become the goal.
- **Vector database** — heavy dependency; compaction (B2) plus notes (B3) cover the need.
- **AST / dependency-graph analysis** — speculative, and not how the reference agent works (plain read/search/edit tools plus a good loop).
- **A classifier model for tool approval** — adds an LLM call to every tool use on an already-constrained free tier (2 round trips per tool call measured; daily request cap already hit); C3's permission rules give most of the benefit deterministically.
- **Per-turn multi-model routing** — multiplies calls on the same budget.
- **A "Global" CI/CD dual mode** — a product pivot, not a feature.

* ### Step 3.8: Diagnosis — open_app picking the wrong app (Obsidian/VS Code instead of the actual text editor)
- root cause, confirmed by reproduction: _match_app()'s substring check was one-directional (`query in n`). Any extra word in the model's query ("text editor app" vs the installed name "text editor") made the query LONGER than the app name, so it could never be a substring — a silent "no match" on a request that should have resolved cleanly. A trailing period had the same effect.
- with the real query failing silently and no way to see what's actually installed, the model's retry was a blind guess from general knowledge (Obsidian, VS Code — both plausible "text editors", both happen to be installed) instead of an informed choice. Both open_app/open_file skip confirmation (by design, non-destructive), so the wrong guess launched immediately.
- fix 1: _match_app() now does whole-word containment both ways via _contains_words() (regex word tokens + set membership), not raw substring. First attempt (raw bidirectional substring) introduced a regression caught before shipping: a one-letter installed app named "R" substring-matched almost any query ("r" is inside "editor"); word-boundary matching fixes both problems at once. (tools.py)
- fix 2: on zero matches, _match_app() now offers difflib.get_close_matches() suggestions instead of a bare "no match" error, so a retry (if needed) is grounded in real installed names. (tools.py)
- fix 3: new list_apps() tool — lists every installed app's display name; SYSTEM_PROMPT now tells the model to try the user's generic phrase first, and if that fails, call list_apps and pick the closest real entry rather than guessing a specific brand from general knowledge. (tools.py, llm_provider.py, cli.py status phrase)
- verified live: "Open the text editor app for me." -> open_app(name="text editor") (the model's literal wording now round-trips correctly) -> launched the real Text Editor, not Obsidian/VS Code. "Open the note-taking app." (genuinely ambiguous) -> model called list_apps first, then picked a real installed name from the result instead of guessing a brand.

* ### Step 3.9: close_app — close a running application
- mechanism: no wmctrl/xdotool installed in this environment (checked), and the session is Wayland anyway where window-based closing is unreliable — so it closes via process signal, not a window-manager close request. Resolves the name via the same _match_app() as open_app, reads the app's Exec= line (_binary_name()) to get its actual process name, then `pkill -f <binary>`. pkill exit codes handled distinctly: 0 = closed, 1 = "does not appear to be running", other = error with pkill's stderr. (tools.py)
- requires user confirmation — unlike open_app/open_file (not destructive), closing an app can lose unsaved work, so it follows the same policy as run_command/delete_file/write-git. Assistant._confirm_prompt() gained a close_app case: "close: <name>". (assistant.py)
- cli.py TOOL_STATUS: close_app -> "Closing calculator...". SYSTEM_PROMPT mentions the new tool.
- verified live end-to-end through the model: "Open the calculator app." -> opened (PID confirmed) -> "Now close the calculator app." -> confirm_run was called with "close: calculator", tool ran, process confirmed gone via pgrep.

* ### Step 3.11: Diagnosis — a request hung for 3+ minutes instead of failing
- user reported "close the text editor" hung >3min and never completed. Checked the assumption it was OpenRouter's daily free-tier cap — ruled out: that fails in under a second with a clear 429 (observed directly, same session). A silent multi-minute hang is a different signature.
- root cause, found by reading the code: OpenRouterProvider.reply()'s requests.post() had no `timeout=`. requests has no default timeout, so a free-tier backend that accepts the connection but stalls (or a slow server-side fallback handoff among the `models` list) hangs the call indefinitely — no error, no cap, just silence.
- fix: added `timeout=60` to the request. (llm_provider.py)
- verified the fix actually bounds the hang, not just added the parameter: (1) a raw socket server that accepts a connection and never responds — requests.post now times out in exactly the configured window instead of hanging; (2) the same scenario driven through the real Assistant.ask() — the resulting exception surfaces cleanly and is already caught by cli.py's generic `except Exception as e: reply = f"I ran into an error: {e}"`, so no other code needed to change.

* ### Step 3.14: Diagnosis — closing an app "takes forever"
- measured, not guessed: instrumented per-API-call timing on a real "close the calculator" request. Finding: the model made ONE api call, and that call returned no tool_calls at all — just the text "Are you sure you want to close the Calculator app?". close_app was never invoked.
- root cause: SYSTEM_PROMPT rule 5 said "...unless the action is destructive... [then ask for permission]" — telling the model to verbally confirm destructive actions in prose, duplicating the tool-level confirm_run gate that _confirm_prompt()/Assistant already handles (close_app, delete_file, run_command, git writes). Confirmed by following up with "Yes, close it." in the same session: only THEN did close_app actually get called. So a single "close X" request cost two full user turns (two LLM round trips plus the user having to notice, read, and answer a text question) before the real, tool-level confirmation prompt even appeared — not a latency problem, a redundant-confirmation-loop problem.
- fix: reworded rule 5 to say tools that require confirmation should still be called directly — the confirmation happens automatically via the tool's own gate, so asking in words first is explicitly forbidden as a redundant round trip. (llm_provider.py)

* ### Step 3.35: B2 — auto-compaction
- design questions resolved before writing code, since this was the first Stage B item with real open decisions rather than an obvious default: trigger = a manual `/compact` command OR automatically whenever the char budget would otherwise drop history (the user's own framing, verbatim); mechanism = a dedicated LLM summarization call (not piggybacked on the next real request, since piggybacking would corrupt that request's actual conversation with an unrelated summarization instruction); persistence = self.history/Store are **never mutated** — compaction only changes what `_context()` builds for a given request. * ### Step 3.52: a serious, real hang bug — subprocess calls inherited the real terminal's stdin
- user report: "when I launch some commands, the terminal freezes (not even ctrl+C works)." The "not even ctrl+C" detail was the key clue, not a throwaway detail: it pointed at something blocked in a way that doesn't go through R.A.V.E.N's own Python-level KeyboardInterrupt handling at all -- i.e. not a slow/looping Python computation, but a lower-level OS-level block.
- root cause, found and reproduced before writing a single line of fix: `tools._run_shell` (backing `run_command`, `run_tests`, and `git`, which delegates to `run_command`) called `subprocess.run(command, shell=True, capture_output=True, text=True, timeout=timeout)` with NO `stdin=` argument. Per ordinary, well-documented Python/Unix subprocess semantics, an unset stdin is INHERITED from the parent -- R.A.V.E.N's own stdin, which in the real interactive CLI is the user's actual terminal. Any command that tries to read input -- `python3` with no args (drops into a REPL), `ssh`, `sudo`, `git commit` with no `-m` (opens `$EDITOR`), `less`/`vim`/`nano`, a bare `read` in a shell script, and plenty of other everyday commands -- blocks reading from that inherited terminal, waiting for input that will never come (the user is looking at prompt_toolkit's own prompt, not typing into the subprocess). Explains "not even Ctrl+C works" precisely: prompt_toolkit already owns the terminal in its own raw input mode for its own line-editing, so a stray Ctrl+C keystroke doesn't get translated into a normal SIGINT the way it would in a plain shell -- there's no ordinary Python-level `KeyboardInterrupt` for R.A.V.E.N's own code to catch, because R.A.V.E.N's own code isn't what's blocked; a child process's syscall is.
- reproduced for real before fixing anything, not just reasoned about: first confirmed the mechanism in isolation (`subprocess.run('cat', shell=True, stdin=<a real pty>, timeout=3)` genuinely hangs until the timeout, `stdin=subprocess.DEVNULL` returns in ~5ms instead), then reproduced it through the ACTUAL `tools.run_command` function with the ENTIRE TEST PROCESS's own real stdin file descriptor (fd 0) redirected to a real pty via `os.dup2` -- the closest possible simulation of the real interactive CLI's exact condition -- confirming the bug was real end-to-end through the real code path, not just in a standalone snippet, before the fix, and confirming the fix resolves it (0.005s, no hang) after.
- fix: `stdin=subprocess.DEVNULL` added to `_run_shell` (covering all three affected tools at once) and, for consistency/defense-in-depth even though they're lower-risk (fixed, code-constructed argument lists, not `shell=True`, not model-controlled strings), to the two other `subprocess.run` calls in `tools.py` (`pkill` for `close_app`, `gdbus call` for Window Calls). A subprocess getting EOF immediately on stdin (DEVNULL's behavior) makes any command expecting interactive input fail or exit fast instead of hanging -- there was never a legitimate reason for a model-triggered subprocess to have real interactive stdin in the first place, since the model can't type into it regardless.
- 2 new tests: the existing `run_tests` fake-subprocess test extended to also assert `stdin=subprocess.DEVNULL` was passed; a new test confirming ALL THREE `_run_shell` callers (`run_command`, `run_tests`, `git`) consistently pass it, not just one. Deliberately did NOT add the pty/fd-redirection reproduction itself as a routine suite test -- reassigning the TEST PROCESS's own stdin fd is a real, if small, risk to pytest's own I/O/capture machinery if anything went wrong, better suited to the one-off live verification already described above (and recorded here) than baked into every future test run. Full suite: 360 passed (351 + 9 `test_browser.py`, run together this time), 12 deselected, real `~/.raven/history.db`/`~/.raven/memory/` confirmed untouched.
- broader takeaway worth stating plainly: this bug existed since `run_command` was first written, long before this session -- the confirmation/safety system this project has iterated on so carefully (SAFE_COMMANDS, the C3 permissions work, etc.) governs whether a command is allowed to run, not whether it can hang the whole session once it does. Those are genuinely different concerns, and this step closes a real gap in the second one that the first one was never designed to catch.

* ### Step 3.67: reduce API latency -- reuse HTTP connections instead of opening a fresh one per call
- user question: is there a way to reduce latency between requests, ideally by tweaking the API-calling methods themselves.
- measured before changing anything (this project's own standing discipline): both `OpenRouterProvider` and `NvidiaProvider` called the bare `requests.post()`/`.get()` module functions -- which, per `requests`' own implementation, build and tear down a throwaway `Session` (and its connection pool) on EVERY call, so every single API call pays a full fresh TCP+TLS handshake, even multiple calls back-to-back in the same process. Timed live against both real endpoints (5 sequential calls each): OpenRouter's `/v1/models` averaged ~1.1s per call with a plain `requests.get()` and NO improvement across repeats (no reuse happening at all); a single shared `requests.Session()` reused across the same 5 calls averaged ~300-400ms after the first -- roughly a 60-70% cut per call. Same pattern confirmed against NVIDIA's endpoint.
- why this matters MORE than a one-off call: one conversation turn commonly makes SEVERAL sequential provider calls -- each tool-call round trip in `Assistant.ask()`'s loop is its own `reply()` call, and `NvidiaProvider`'s client-side fallback makes two calls back-to-back on a failure -- so the saved handshake compounds within a single turn, not just across turns.

* ### Step 3.69: desktop UI -- cancel an in-flight request
- user request: add the ability to cancel a request in the desktop UI.
- design constraint that shaped everything else: `Assistant.ask()` runs inside `asyncio.to_thread` -- a REAL OS thread, not a coroutine -- so unlike the CLI's own `Ctrl+C` (a genuine `KeyboardInterrupt` the OS delivers straight into the blocking call, which `Assistant.ask()` already catches and rolls back from) nothing server-side can forcibly stop that thread mid-network-call. Cancel is therefore "stop caring about the answer and roll it back once it arrives," not a true abort -- stated plainly rather than oversold.
- `raven/server.py`: new `_AskToken` (one per in-flight `ask()`, so `cancel_ask` marks exactly THAT call, never a later one started after settling); `Session._ask_token`. New `cancel_ask` message: marks the current token cancelled, acks immediately with `cancel_requested`, or a clear "Nothing to cancel" error if none is in flight. `_run_ask` now takes that token: on settle, if cancelled, rolls the turn back (`del self.assistant.history[checkpoint:]`, mirroring `Assistant.ask`'s own `KeyboardInterrupt` handler) and sends `cancelled` instead of `reply` -- including when the (still-running) call ALSO happens to fail, which reads as a cancellation to the user, not a scary unrelated error. A second `ask` while one is already in flight (cancelled or not) is now refused with a clear error -- this closes a real, previously-latent gap (nothing stopped two concurrent `ask()` calls from mutating `self.assistant.history` from two different threads at once; the UI's own disabled Send button was the only thing preventing it).
- **known limitation, found and stated rather than silently accepted**: `Assistant.ask()` calls its own `_persist()` (writes to the SQLite store) before returning control to `_run_ask`, i.e. before `_run_ask` even learns the call was cancelled -- so the rollback is complete for the LIVE conversation (`self.assistant.history`, what the model and the UI's `get_history` both actually read for the rest of this session) but the discarded turn is still sitting on disk; a full app restart afterward would load it back. The CLI's own `Ctrl+C` avoids this because there, cancellation is a `KeyboardInterrupt` raised INSIDE `_run_turn`, propagating out before `_persist()` is ever reached -- not available here since a background thread can't be interrupted that way. Not fixed (would need a new `Store` method to delete specific rows after the fact); the common case (keep using the session) is already correct.
- `raven_ui/src/useRaven.ts`: new `cancelling` state (true from `cancel_ask` sent until `cancelled` arrives -- `busy` stays true the whole time, so the composer can't be used to send a new message while the old one might still be mutating history in the background) and `cancelAsk()`. `cancel_requested`/`cancelled` wired into the message switch; `cancelling` also feeds the existing "thinking word" rotation effect, showing "Cancelling..." in place of the random word/tool status.
- `Composer.tsx`: the Send button becomes a Cancel button (danger-colored, outlined) while `busy`; label switches to "Cancelling..." and disables itself once cancellation has actually been requested, so a repeated click can't fire twice. `ChatStage.tsx`/`App.tsx` thread `cancelling`/`onCancel` through.
- verified: 9 new `raven/server.py` tests using a REAL `Store` (a mocked `.reply()` blocks on a `threading.Event` so the test can genuinely send `cancel_ask` while the call is still running, not just simulate it) -- immediate ack then eventual `cancelled`; the exact cancelled user message/reply text confirmed absent from `get_history` afterward (the stronger, live-history check); the STORE still having the persisted-but-discarded turn is asserted too, matching the documented limitation rather than hiding it; a second `ask` while one is in flight is refused; a fresh `ask` right after a cancelled one settles goes through normally (the refusal isn't permanent); a cancelled call that also errors reports `cancelled`, not `error`. Full suite: 514 passed, 3 runs in a row. Frontend: `tsc --noEmit` clean; a real headless-Chromium run against a mocked, deliberately-never-replying server confirmed the whole visible cycle -- Send -> "Cancel" button appears -> click -> "Cancelling..." (disabled) -> (simulated settle) -> "Send" restored, textarea re-enabled, exactly the messages `ask`/`cancel_ask` sent to the server and nothing else.

No true mid-flight network abort (see the design-constraint note above) -- a cancelled call can still take up to its full 60 s timeout to actually settle in the worst case, during which the composer stays disabled.

* ### Step 3.74: Step 3.73's sudo fix was itself broken -- two real bugs found from a live user report
- user report, pasted verbatim terminal output: asked R.A.V.E.N to "install notion for linux on my computer"; approved `sudo snap install notion`; the NEXT tool call's `Allow?` confirmation appeared, then REAL, native sudo prompt text ("Sorry, try again." / "[sudo] password for ely:") started interleaving with it mid-prompt, garbling both, ending in "Cancelled." That's the interleaving the user saw.
- fix: new `tools._run_capturing_group` (`subprocess.Popen(..., start_new_session=True)` + `.communicate(timeout=...)`, catching `TimeoutExpired` and killing the WHOLE process group via `os.killpg(os.getpgid(proc.pid), signal.SIGKILL)` before draining) replaces the bare `subprocess.run` calls inside `_run_sudo` specifically (the general non-sudo `_run_shell` path is untouched -- this class of bug matters far more for a command that can open a real tty and hold it hostage than for an ordinary command, and widening scope further wasn't asked for). - verified: **live, with real orphaned processes, not just unit tests** -- `_run_capturing_group("true; sleep 36", timeout=1)` timed out in 1.00s with NO surviving `sleep 36` process afterward (re-ran the same shape against the OLD plain `subprocess.run` first, to confirm the orphan is real and reproducible, then against the fix, to confirm it's gone). Rewrote the 4 existing Step 3.73 sudo tests (now against `subprocess.Popen`/`.communicate()` instead of `subprocess.run`, since the implementation changed) plus 2 new ones (the real authenticated call gets `RUN_SUDO_TIMEOUT`, not `RUN_COMMAND_TIMEOUT`; a hung command's whole process group gets killed, verified via a fake `Popen` that only stops "hanging" once `os.killpg` is actually called -- proving the kill happens BEFORE the drain, not just eventually). Full suite: 545 passed.
- not done: the general (non-sudo) `run_command`/`run_tests` path still uses plain `subprocess.run` with only wrapper-level timeout killing -- same theoretical orphan risk exists there for any long-running compound command, but it can't hijack the real terminal the way an orphaned `sudo` can (nothing else opens `/dev/tty` on its own), so it wasn't in scope for this report and wasn't changed.

* ### Step 3.75: desktop UI -- Copy never actually worked, in either form the user tried

## Clarifications

* MAX_TOOL_ITERATIONS (assistant.py): Without it, a single ask() call could loop forever.

The loop is: ask model → model calls a tool → feed result back → ask model again → maybe it calls another tool → repeat. There's nothing structurally stopping the model from just kept calling tools indefinitely — e.g. it misreads a file, keeps retrying to "understand" it, or gets into a confused back-and-forth where it never settles on a final text answer. Free/smaller models are more prone to this kind of not-quite-right behavior than larger ones.

Concretely, without the cap: one bad request could hang your terminal, burn through your OpenRouter rate limit (20 req/min free tier), and potentially run several confirmed shell commands in a row before you realize something's wrong.

MAX_TOOL_ITERATIONS = 5 just guarantees the function always returns — worst case you get "I hit the tool-call limit" instead of an infinite loop.
